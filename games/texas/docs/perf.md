# 德州扑克：画面性能实测

> 结论和由此定下的约束在 [screens.md](screens.md) 8.7；这里是怎么量的和量到的数。

背景和毡面上的多层斜纹（`repeating-linear-gradient`）曾被怀疑会被动画和文字变化反复重绘。实测方法：无头 Chromium 模拟省内存手机（844×390、像素比 2、触屏、CPU 降速 4 倍），自动打 4 手左右，读主线程总占用（`Performance.getMetrics` 的 `TaskDuration`），
用注入样式的办法对比去斜纹、独立合成层、纯色背景、去阴影、去动画、去过渡等方案，每个方案跑两轮以上。

结论：画面在降速 4 倍的手机上主线程占用约 11%（折算不降速约 3%），脚本只占约 0.5%，样式重算 1–2%。各方案的差别都落在 ±3 个百分点的噪声里，没有一个稳定更省，所以**不为性能改 CSS**：
去斜纹会丢掉毡面的织纹质感，加独立合成层会多吃老 iPhone 的内存。唯一看得出的下降来自整页关掉动画和过渡（约 9%），而动画本来就是画面要的反馈。以后要再优化，先用 Chrome 的性能面板看具体哪一帧在画，而不是猜样式。
（皮肤换成卡通以后这套方法仍适用，数字没有重测。）

## 打开和对局的测量（`scripts/perf.ts`，0.40.1）

`npm run build:cf && node scripts/perf.ts [--runs 3] [--play 40] [--out 结果.json] [--profile 目录]`：真的 Worker + 冒烟的假平台，电脑 1280×800 和手机竖屏 390×844（CPU 降速 4 倍）各跑几遍取中位数，
量主页（FCP、LCP、可交互、长任务和超出 50 毫秒的部分之和 TBT、传输字节）、选桌页打开、对局中按默认动画速度打 40 秒（帧间隔 p50/p95/p99、长任务、JS 堆），以及带哈希的资源是不是 immutable。
前后比较要背靠背：同一台机、同一口径连着跑，经 browser-slot 的 exclusive 占满浏览器位子（别的代理同时跑会把长任务量多一倍）。`--profile` 存手机那一遍的 CPU 采样（看函数名先 `vite build --minify false`）。

0.40.1 前后（各 3 遍中位数，毫秒）：

| | 电脑 改前 → 改后 | 手机（降速 4 倍）改前 → 改后 |
|---|---|---|
| 主页 FCP | 144 → 132 | 528 → 368 |
| 主页 LCP | 344 → 332 | 640 → 452 |
| 主页可交互 | 150 → 136 | 652 → 464 |
| 主页 TBT | 21 → 14 | 375 → 218 |
| 选桌页打开 | 48 → 55 | 136 → 126 |
| 对局中帧间隔 p99 / 长任务 / 最长 | 16.8 / 0 / 0 → 不变 | 16.8 / 2 / 84 → 16.8 / 1 / 62 |
| JS / CSS（gzip，KB） | 148 / 26 → 不变 | 同左 |

找到并改掉的根因：
- 主页打开时整页排了两遍：`buildShell` 建完整页才量视口（读根节点尺寸，逼出一次整页排版），量完改舞台大小又得整页再排。现在先建舞台、量好尺寸，再往里建页面，量的时候几乎是空页。
- 牌桌藏着（标题页、选桌页）时还在量荷官站位（`placeCroupier`），又逼一次排版；现在藏着时按第一个点摆、进桌再量。
- 筹码数字每次 `toLocaleString`（每次现查区域设置）：改成复用一个 `Intl.NumberFormat`。
- 带哈希的 JS、CSS 原来是 `max-age=0, must-revalidate`，每次打开都回源校验；`_headers` 改成存一年、immutable（`build:cf` 拷到 `dist-cf/_headers`，首页过 Worker 不受影响）。
  冒烟的假平台开了请求拦截，Playwright 这时不用 HTTP 缓存，所以"再次打开"量不出来，只核对头。

没改的：剩下那个长任务主要是首次排版（无头 Linux 里第一次找中文字体回退约占一半，真机不同），脚本执行只占约 20 毫秒；
JS 一个包 148KB（gzip），按需拆出好友房、谜题、分享能省约 13%，但主页可交互几乎不受脚本大小影响，要把页面装配改成异步，这一批不做。
开桌到底牌翻开约 3 秒是发牌动画的节奏，不是卡顿（CPU 只忙约 0.4 秒），电脑上这项随发牌顺序在 2.9–3.4 秒之间跳。
